## 1. 项目是什么

`autogame`：全自动刷图机器人。链路是

```
采集（摄像头/HDMI/截屏） → 检测（Detector） → 决策（FSM + 恢复阶梯 + VLM/LLM 顾问）
   → 指令（Command 协议） → 执行（RP2040 HID / 树莓派 GPIO / DryRun）
```

落地形态：**RK3566 小主机**跑服务端 + 摄像头看屏幕 + HID 板子发鼠标键盘。
配置页在 `http://<设备IP>:8765/settings`，仪表盘在 `/`，审查页在 `/review`。

铁律（不可绕过，测试会盯）：
1. 场景门说"不是战斗界面"→ **一条指令都不发**；
2. 没看到 A 框 → 绝不按拾取键；
3. 同一个位置不连续盲点；不停手不盲点。

## 3.5 LLM 监督层（11-18 新增，默认 shadow）

用户的原话：「opencv 做指令一定最快，但准不准、覆盖全不全，还得加个大模型判断结果
是否正向，还有应对突发情况。」

落地成 `autogame/decision/supervisor.py`。**它不是驾驶员，是断路器和审计员。**

### 为什么不能每帧问模型

| 问题 | 现实 |
|---|---|
| 延迟 | 本地 7B 1~3s，云端 2~15s。每帧都问，1Hz 变 0.3Hz |
| 成本 | 一小时 3600 帧 |
| **方差** | 视觉阈值确定可回归；LLM 每帧答案会飘。拿飘的东西逐帧控制比开环更差 |

### 它有什么权力（这条线不能松）

| 结论 | 效果 | 门槛 |
|---|---|---|
| `allow` | 无 | — |
| `throttle` | 走位/点击间隔 ×2 | conf ≥0.60 |
| `hold` | 本帧不发命令，**≤6s 自动放行** | conf ≥0.60 |
| `takeover` | 只许 `esc`/`wait`/`reset_stage` | conf ≥0.80 + evidence 必须复述输入数字 |
| `panic` | 停车交人工 | ≥0.80 + 证据 + **连续 2 次** |

`stop_all` 永远放行。接管动作带坐标 → 直接降级 hold（**模型不许指路**）。

### "结果是否正向"是算出来的，不是问出来的

FSM 在关键动作后登记预期，到期用实测值结算：

| 动作 | 预期 | 实测 | 判定 |
|---|---|---|---|
| 走位 | 距离缩短 | 237→241 | miss |
| 按拾取键 | A框消失 | A框仍在 | miss |
| 按 ESC | 回到战斗 | 仍不在 | miss |

喂模型的是这串数字 + 健康指标（拾取增量/空转时长/意图抖动），**不传截图**。
文本更快更便宜，而且"看图会编"。

### 怎么验证（不用装模型）

```bash
py -3.12 tools/supervisor_demo.py             # shadow：看它想拦什么，但一条不拦
py -3.12 tools/supervisor_demo.py --enforce   # enforce：真的拦，对比命令数
```

实测输出：假走位 24 帧 → 3 次落空后触发 → 模型判 hold → enforce 下 48 条命令拦掉 14 条。

### 上线节奏（别跳步）

1. `mode: shadow` 跑 3~5 小时；
2. 看 `logs/supervisor.jsonl`，每条都有 health + evidence；
3. 人工判断："它想拦的这 N 条，我认不认？"
4. 全认 → 切 `enforce`；有一条不认 → 先改触发阈值或 prompt，别切。

**没有影子期的监督层不该上线**——它会变成新的故障源。

## 3.6 三级裁决（11-18 新增，默认 shadow）

用户提出："先分析页面出现的东西，有截图和文字介绍的直接处理；稍微不明白才让 laya 判断，
问 laya 时要把系统已支持的行为提前准备好；行为不满足选 others 才请求大模型；
问的时候人物不能站着不动；这次行为要作为经验存出来，和整理的游戏内容放一起。"

### 三级与代价

| 级 | 触发 | 代价 | 能不能发动作 |
|---|---|---|---|
| L0 经验直出 | 同指纹 + `confirmed` | **0 次模型调用** | 能（已验证的） |
| L1 laya | 闲置 / 未标定 / 连续落空 | 1 次小模型（1~3s） | 能（从清单单选） |
| L2 大模型 | L1 返回 others / 选越界 / 置信不足 | 1 次大模型（3~15s） | 能（计划，≤5 步） |

### 文件

- `autogame/decision/actions.py` —— 行为清单 + 参数校验（禁坐标）
- `autogame/decision/knowledge.py` —— 局面指纹 + 经验状态机
- `autogame/decision/arbiter.py` —— 三级裁决 + 后台线程 + 保命
- `autogame/decision/llm_client.py` —— 模型调用唯一出口（supervisor 也可复用）
- `fsm.action_table()` —— 清单的**实现端**。清单描述，FSM 决定"真能不能做"
- `profiles/<id>/knowledge/game.md` —— 人写的玩法说明（进 prompt，优先级最高）
- `profiles/<id>/knowledge/experiences.jsonl` —— 机器沉淀的经验

### 三条不能松的约束

1. 参数里出现坐标（x/y/px/pos）一律拒。模型只决定"做什么"，不决定"去哪"。
2. L2 计划里一步做不到 → **整条丢弃**，不执行残缺计划。
3. 经验 `candidate` 不许直出，只有 `confirmed` 能进 L0。

### 为什么经验要分状态

模型第一次给的做法只是 `candidate`；真执行过、对账确认有效（拾取数涨了/怪少了/回战斗了）
两次，才升 `confirmed`；错两次降 `rejected` 并保留 —— 保留是因为"别这么做"对模型有价值，
`knowledge.prompt_block()` 会把 rejected 一起给它看。

对账判不出来时记 `unknown` 不硬判（比如 `explore` 走了多远没法从现有字段测）。
宁可不升级，也不要让噪声把错经验推成 confirmed。

### 现在缺什么

- `_post` 两条路（ollama / openai）**都没接过真模型**，`tools/arbiter_demo.py` 用的是假回复。
- 对账只覆盖 `pickup` / `attack_nearest` / `esc` / `rechallenge`；`explore` / `navigate`
  的位移无法从现有 SceneState 测出来（记 unknown）。
- `game.md` 里大量"待补充"：背包/结算界面、紫色/蓝色稀有度配色、是否用文字标签标掉落。

## 3.7 教学编译（11-18 新增）

用户的原话：「每个游戏都要有这些内容，我希望有一个过程让程序吃掉并完全理解用户写的东西。」

`autogame/teach.py` + `tools/teach.py`：把 `profiles/<id>/lessons/*.md` 编译成
台账条目、`game.md` 受管块、`glossary.json`、待办清单。

**"理解"被定义成三条归宿，没有第四种**：可验证的判据 / 进模型上下文的文字 /
明确的待办（缺图、缺框、键位冲突、阈值不符）。每条 claim 都带 `文件:行号`，
报告能逐条回溯到人写的那句话。

格式：`## 类型 · 标题` + `- 字段: 值`，六种类型 `界面/物体/流程/键位/禁忌/术语`。
HTML 注释会先被剔除（保留行号）——注释里写 `## 界面` 的示例不会被解析成幽灵条目。

三个约束（都有测试钉住）：
- **核对不过不许 strict**：条目仍入库，`strict=false` + 原因写进 note。缺口可见，CI 不瞎。
- **已有条目绝不覆盖**：`labels.json` 只追加不存在的 file，人的 note 永不改写。
- **量不到就说量不到**：没框不编高宽比，没图不编颜色。

`glossary.json` 被 `KnowledgeBase.prompt_block()` 读进模型上下文，标成"用户说这些词时
指的是下面的意思"——这是解决"用户的黑话模型按通用含义理解"的那一环。

现在 `tli_phone960` 编译结果：13 条 claim，一致 5、缺料 5、文字类 3、不一致 0。
缺的是背包/角色面板/结算三类截图、一束真实掉落光柱（带框）、以及「攻击」的键位。
