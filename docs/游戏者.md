# 游戏者：教程序玩，而不是给每款游戏写适配器

一句话：**这个程序不是"支持 N 款游戏的模拟器"，是一个能被教会玩任何游戏的玩家。**

加一款新游戏时，不改代码，只补三份文件：操作方案（哪个键干什么）、技能（这件小事分几步）、
目标（先干什么）。做到做不到，程序自己会说；说了不算的地方，它会停下来，而不是照脚本按一晚上。

---

## 1. 为什么不做"每款游戏一个适配器"

适配器路线的代码会长成这样：

```python
if game == "torchlight":  left_click_move(); right_click_attack()
elif game == "wow":       wasd(); press_1(); tab_target()
elif game == "d4":        ...
```

每加一款要动一次核心，每动一次都要重跑一遍全部回归；而"这款游戏该怎么刷"本来是**玩家脑子里的
知识**，不是引擎能力。把知识写进代码，等于每次换游戏都请程序员改一遍。

但也不能把什么都做成可配的 —— 有一类东西必须钉死：

| | 例子 | 能不能教 | 为什么 |
|---|---|---|---|
| 键位 | A 是拾取、右键是主攻 | 能 | 教错了顶多捡不到，看得见 |
| 技能 | 先走近、再打、再捡 | 能 | 教错了是效率问题 |
| 目标 | 先刷图、包满了回城 | 能 | 教错了是策略问题 |
| **铁律** | 没 A 框不许按拾取键 | **不能** | 一旦可教，"学"就会把安全学松 |

所以分层是：**知识和铁律分开，知识可教，铁律写死在动词里。**

---

## 2. 四层结构

```
goals      目标：现在想干什么                YAML，随便改
skills     技能：分几步、每步做到什么算完      YAML，随便改
cues       判据：画面哪里、读什么、多少算成立   YAML，按截图标定
verbs      动作：走/打/捡/交互/开面板/放技能   代码，证据写死
effects    效果：做了之后世界变没变           代码，只累计证据
```

- `verbs`（`autogame/agent/verbs.py`）与游戏无关。它只知道"有目标才能走"、"有 A 框才能捡"
  这类**任何游戏都成立的常识**。方案的键位由 `InputScheme` 提供，动词自己不知道 A 是哪个键。
- `skills`（`skills.yaml`）是"怎么干一件小事"：走到 → 捡 → 直到那个目标消失。
- `goals`（`goals.yaml`）是"为什么干"：刷图、回城、清任务，按优先级排。
- `cues`（`cues.yaml`）是"什么时候按"：蓝够不够、CD 到没到、脚下有没有东西（第 5 节）。
- `effects`（`effects.py`）回答"按了有没有用"。它是"照脚本按"和"会玩"的分界线。

每帧只做四件事，一步不循环（帧驱动的老规矩，循环会把帧读空）：

```
1. 结账：上一次动作之后世界变了没有
2. 选目标：没有目标、或原目标做不下去 → 挑下一个"现在真的做得到"的
3. 推进技能一步：拿到一个动作意图，或这帧什么都不做
4. 发出去：命令交给执行器（或测试收集器）
```

## 3. 三条"不假装"

"假运行"（界面显示在跑、实际什么都没做）有三个来源，这里各有一条计数器：

| 计数器 | 含义 | 处理 |
|---|---|---|
| `blocked_capability` | 技能用到这个游戏没教的能力 | **立即中止技能**，不重试到超时 |
| `blocked_evidence` | 想按但没有证据（没 A 框、没目标） | 这一帧不按，下一帧再看 |
| `noop_completion` | 技能"成功"了但一个动作都没发 | 记一条警告，三次之后封掉这条技能 |

为什么 `blocked_capability` 不许重试：没教拾取键时重试 20 秒，产出的只是一堆"看起来很努力"的
按键，日志全绿 —— 比直接停下更难查。

为什么 `blocked_evidence` 要计数：它是**铁律真的在生效**的证据。这个数应当是正数；恒为 0 说明
它一直在盲按。

按键类动词还要过一道**帧时效**闸（`fresh`，上限 `agent.max_frame_age_ms`，默认 400ms）：
A 框只是"过去某一帧在范围内"，帧一旧人就可能已经走过去了。这条和 FSM 里的
`decision.press_max_frame_age_ms` 是同一个闸，游戏者层不能因为"换了套逻辑"就少一道。

## 4. 效果账本：从"按了"到"有没有用"

只比语义，不比像素。像素差永远非零（特效、飘字、光照），那样每条动作都会被判成"有用"。

按动词分两种口径：

- **位移类**（`move_to` / `roam`）：看画面有没有动。相机跟随时角色恒在屏幕中心，位置签名不变，
  只能靠画面变化量。
- **状态类**（`pickup` / `attack` / `interact` / `use_skill` / `open_panel`）：看语义状态
  （地上东西少了一个、怪变少、界面切走了）。把"画面在动"算进来，飘个特效就会被当成"捡到了"。

同一动作在同一情境下累计 `dead_after` 次都没有效果，就吐出一条**待验证假设**：

```
「attack」在「combat」情境下按了 4 次，画面一次都没变
  → 先确认主攻键是「按住」还是「连点」，再确认目标选择器是否真的选中了怪
```

**它只提案，不改任何配置。** 攒够证据、人点头之后才走已有的补丁通道（`PatchStore`，可回滚）。
这条边界和"方案里没有 when 字段"是同一个理由：可教的东西不能包括铁律。

## 5. 判据：什么时候按，是画面说了算

技能能写出来，不代表能跑。`use_skill` 缺的从来不是"按哪个键"（方案里有），
而是**什么时候按**：蓝够不够、技能在不在 CD、脚下有没有可交互的东西。

这些字段不在 `SceneState` 里，也不该在 —— 每款游戏的血条位置、图标样式都不一样，
塞进协议就是把协议变成某一款游戏的形状。所以单开一层：

```yaml
# profiles/<id>/agent/cues.yaml
cues:
  - id: mana_ok
    kind: ratio                          # 这块区域里"像这个颜色"的像素占比
    region: [0.03, 0.88, 0.12, 0.906]    # 归一化，换分辨率不用重标
    color: "#2a6bd4"
    above: 0.5                           # 占比过五成才算"蓝够"
```

技能里就这么用（`when` 写条件名，`cue` 指哪一条）：

```yaml
- verb: use_skill
  slot: fireball
  when: cue
  cue: mana_ok
```

三种读法：

| kind | 读什么 | 典型用途 |
|---|---|---|
| `ratio` | 区域里接近 `color` 的像素占比 | 血条/蓝条、光柱、按钮染色 |
| `bright` | 区域平均亮度 | 黑屏、加载遮罩、面板变暗 |
| `template` | 模板匹配最高分 | 图标、按钮、交互提示位 |

模板类的阈值就是 `min_score`，不用再写一遍 `above` —— 一个阈值写两处，
迟早出现"改了 min_score 忘了 above"，那时判据按旧值成立、模板早就不匹配了。

**阈值不手填。** 手填的数字没人验证得动，两周后也忘了当时凭什么填：

```bash
# 先看这块区域主要是什么颜色
py tools/learn_cue.py --profile tli_phone960 --image 蓝满.png --region 0.03,0.88,0.19,0.906

# 给"成立 / 不成立"两张截图，它取中间值、写进 cues.yaml
py tools/learn_cue.py --profile tli_phone960 --id mana_ok --name 蓝量够 \
    --region 0.03,0.88,0.19,0.906 --color "#2a6bd4" \
    --on-img 蓝满.png --off-img 蓝空.png --write

# 模板类：直接从截图裁一块
py tools/learn_cue.py --profile tli_phone960 --id chest_hint --kind template \
    --region 0.35,0.55,0.65,0.80 --crop 520,430,620,470 --write
```

两组样本的中间值是唯一能自证的数字。以后判错了，回头看也知道当时按哪两张定的。

### 技能循环也在这层

`repeat`（最多几轮）+ `until`（满足就收手）：

```yaml
- id: pop_skills
  when: monsters
  repeat: 3              # 上限三轮
  until: no_monsters     # 怪清完就不放了
  steps:
    - verb: use_skill
      slot: q
      when: cue
      cue: mana_ok
```

不写 `repeat` 就是一次。**有上限是刻意的**：无上限的循环在"这个技能永远不生效"时
会按满一整晚，而那正是最该停下来的情况。`until` 在**轮边界**判，不在轮内每帧判 ——
否则"打完再捡掉落"这种收尾会被"怪没了"当场砍掉，东西捡不到、日志还全绿。

### 判据读不出来时，往哪个方向倒

| 情况 | 结果 |
|---|---|
| 没有画面（离线回放） | 全部 0，**不是**沿用上一帧 |
| 区域越界 / 模板缺文件 | 0，并记进 `last_errors`，不抛异常 |
| 没写阈值 | lint 报 error（不是"永远成立"） |

方向是一致的：**缺证据只能让动作变少，不能让动作变多。** 反过来就是"画面一片黑也照按"。

最后还有一条假设：某条判据读了几百帧一次没成立，`hypotheses()` 会吐一条
「可能区域标错了，也可能这局确实没这个条件」。程序分不清这两者，所以两种可能都写上，
交给人判 —— 和"它只提案、不改配置"是同一条规矩。

## 6. 教一款新游戏的五个步骤

```bash
# 1) 键位（问一次，或从预设起步）
py tools/learn_input.py --profile my_game --preset tli_pc --ask
py tools/learn_input.py --profile my_game --ask --capture      # 切到游戏里按真实键

# 2) 判据：有截图就标，没有就先空着（空着的效果是"技能不放"，不是"技能乱放"）
py tools/learn_cue.py --profile my_game --id mana_ok --region 0.03,0.88,0.19,0.906 \
    --color "#2a6bd4" --on-img 蓝满.png --off-img 蓝空.png --write

# 3) 目标与技能：照着 profiles/_template/agent/ 抄一份改
#    profiles/<id>/agent/skills.yaml
#    profiles/<id>/agent/goals.yaml

# 4) 编译一遍：每个目标做得到吗？缺什么？判据写得对不对？
py tools/agent_play.py --profile my_game --check

# 5) 在模拟世界里陪练 10 秒：动作序列、有没有盲按、哪个动作一直没效果
py tools/agent_play.py --profile my_game --seconds 10
```

第 3 步不用一次写全。先写"捡最近的东西"和"没目标时找路"两条，能跑起来再往上加打怪、开箱、
换图。**知识是可以逐步补的，代码不用动。**

要让它真的接管游戏（而不是只在陪练里跑），把 `config.yaml` 里的 `agent.enabled` 改成 `true`
再重启。开着却没有知识时不会静默变成"什么都不做"：服务端会写一条 `agent_off` 事件并留在 FSM 上，
页面的 `/api/config` 里有 `agent_report` 能看到每个目标"做得到/缺什么"。

## 7. 写知识时最容易踩的六个坑

前四个都做成 lint 错误了，因为它们**不抛异常，只是让程序安静地不干活**：

1. **拾取的完成条件写成 `not_aframe`** —— A 框在人还没走到时也不在，这一步会被直接跳过。
   用 `target_gone`（那个目标消失了才算捡到），而且它按**数量**判断，不按屏幕坐标：
   相机一跟，目标在屏幕上就跑了，会被误判成"已经消失"。
2. **`pickup` 前面没有 `move_to`** —— 站在远处按 A 什么也捡不到，而日志一切正常。
3. **`open_panel` 没写 `when`** —— 面板键是无目标按键，战斗里按下去会打断自己。
4. **技能里写 `when: no_targets`，动词却需要目标** —— 自相矛盾，那一步永远不执行。

后两个是判据层带来的新坑，同样是不报错、只是不干活：

5. **判据区域框太大** —— 整屏算占比，任何特效都会把读数带跑，"蓝够不够"永远成立。
   只框确定属于这个状态的部分（蓝条的填充段，不含空槽和边框）。
6. **`repeat` 写了、`until` 没写** —— 会把轮数跑满，怪早清完了还在原地放技能。
   两个一起写：`repeat` 是上限，`until` 是出口。

还有一条不是坑但经常忘：**判据标了却没人用**。`cues.yaml` 里写了 `mana_ok`、
技能里没写 `when: cue`，lint 会报"标了但没人用"——判据不会自己起作用。

## 8. 现在能玩到什么程度（如实）

以火炬之光（PC）为例，`tools/agent_play.py --check` 的输出：

| 目标 | 状态 | 用哪些技能 |
|---|---|---|
| 回到战斗界面 | 可用 | `back_out` |
| 刷图 | 可用 | `fight_group` / `pick_nearest` / `roam_and_look` |

技能层面的覆盖：走位（点地面）、主攻（右键按住）、拾取（A + A 框闸门）、探索（点屏幕边缘）、
面板退出（ESC）、技能循环（`repeat` + `until`，什么时候放由判据决定）、喝药（`hp_low`）。

**还没有的**：开箱/进门的"何时按"、换图/选关 —— 这两项缺的是**截图**（D 提示长什么样、
关卡面板上有哪些节点），不是缺能力。判据层已经能接住它们：有图就能标，标完写进 YAML 就能用。

判据本身现在是 **0 条**（`profiles/tli_phone960/agent/cues.yaml` 是空的，文件里列了要标的四条和
标法）。为什么空着：判据是"这款游戏的画面长什么样"，我没有一张这台手机上的实拍图。
凭空写一组 region/color 的后果是判据恒为 0、技能一次不放 —— 而那和"蓝真的一直不够"
在日志里长得一模一样。宁可在知识检查里看到"判据 0 条"，也不填假数字。

判据这条链路本身是验证过的：`tests/test_cues.py` 用模拟器渲染的真画面跑通了
「画面读蓝量 → 该不该按 → 技能发不发出」的整条路径（蓝满按下、蓝空一个键都不发）。

## 9. 文件清单

| 文件 | 作用 |
|---|---|
| `autogame/agent/verbs.py` | 八个语义动词 + 证据闸（铁律在这里） |
| `autogame/agent/effects.py` | 语义签名、效果分类、无效果账本 |
| `autogame/agent/cues.py` | 判据：区域 + 读法 + 阈值，读不出来一律 0 |
| `autogame/agent/skills.py` | 步骤/条件/技能执行（帧驱动，含 repeat 循环） |
| `autogame/agent/goals.py` | 目标选择（按优先级 + 现在做不做得到） |
| `autogame/agent/knowledge.py` | 加载、lint、报告（页面/预检都吃它） |
| `autogame/agent/runner.py` | `GamePlayer`：把上面五层串成一帧一步 |
| `profiles/<id>/agent/*.yaml` | 每个游戏的知识（goals / skills / cues） |
| `tools/learn_cue.py` | 按截图标定判据（自动算阈值） |
| `tools/agent_play.py` | 知识检查 + 模拟世界陪练（有判据时喂真画面） |
| `autogame/preflight.py::_check_agent` | 上机前编译知识 |
