# 升级引擎：代码整包换，数据原地不动，退得回来

## 一句话分清两件事

| | 谁在动 | 动什么 | 怎么退 |
|---|---|---|---|
| **二次进化** `evolve` | 设备自己 | 配方（`rules.yaml` / 模板 / 经验） | 「退回上一代」，秒级，不重启 |
| **引擎升级** `upgrade` | 只有人 | 代码（整个 release 目录） | 「退回上一版」，切指针，重启生效 |

进化能出代，是因为它只产出**数据**（受限 DSL + 图片 + 文字）。
引擎不能这么干：RK3566 上没有 git、没有编译器，模型改坏一行 Python 就变砖。
所以引擎的规则是反过来的 —— **不能改，但可以换**，而且换的过程必须可验证、可回退。

## 设备上的布局

```
/opt/autogame/
    releases/0.2.0/       引擎（解包出来的只读副本，每个版本一份）
    releases/0.2.1/
    current               一行文本："0.2.1"
    previous              一行文本："0.2.0"（回退用）
    bin/autogame          唯一入口：读 current 决定跑哪个 release
    venv/                 依赖（跨版本共用，升级不用重装）
    upgrade.jsonl         每次装/退的记录
/var/lib/autogame/        数据根 —— 升级一个字都不碰
    profiles/tli_phone960/    图、手册、模板、进化代数
    logs/                     台账
    config.yaml               这台机器自己的配置
    .token                    配对用的 token
    profile                   一行文本：这台机器玩哪个游戏
    snapshots/                升级前的元数据快照
    .schema                   数据布局版本
```

代码根和数据根是**两个目录**（`autogame/paths.py`）。开发机上不设
`AUTOGAME_DATA`，两个根重合，行为与以前完全一致。

## 三个版本号，各管一件事

- `ENGINE_VERSION`（`0.2.0`）：代码版本。
- `DATA_SCHEMA`（`2`）：数据布局版本。引擎只**向后读**，能读
  `MIN_DATA_SCHEMA..DATA_SCHEMA` 之间的数据。
- `RECIPE_SCHEMA`（`1`）：配方 DSL 版本。新引擎必须能跑旧配方，
  否则升级会让设备上已经学出来的规则集体失效。

升级前会先算一次：**目标引擎认不认现在的数据？**
数据太旧（跳版本升级）→ 拒绝，让你先装中间版本；
目标太旧（降级）→ 拒绝，因为新字段会被读丢。

## 三条命令

```bash
# 开发机：打包（默认读 autogame/version.py 的版本号）
python tools/release.py                 # → dist/autogame-0.2.0.tar.gz（+ .sha256）
python tools/release.py --require-clean # 正式版：工作区不干净就失败

# 设备：装（校验 → 自检 → 切指针）
sudo autogame-install autogame-0.2.1.tar.gz
sudo autogame-install autogame-0.2.1.tar.gz --dry-run   # 只看会不会过

# 设备：看 / 退
sudo /opt/autogame/venv/bin/python /opt/autogame/releases/$(cat /opt/autogame/current)/tools/upgrade.py status
sudo /opt/autogame/venv/bin/python .../tools/upgrade.py rollback
```

首次安装（新机器一次）：

```bash
sudo deploy/install.sh dist/autogame-0.2.0.tar.gz
```

## 一次升级到底做了什么

| 步骤 | 失败会怎样 |
|---|---|
| 读 `RELEASE.json`、逐文件比对 sha256 | 不动手。包没下完/被改过，一眼看出来 |
| 检查数据根不在 `releases/` 里 | 不动手。这是"换代码把数据换掉"的唯一入口 |
| 数据 schema 区间检查 | 不动手。提示是"太旧不能跳"还是"这是降级" |
| 磁盘余量（包的两倍） | 不动手 |
| 解包到 `releases/.staging-<ver>/` | 删 staging，指针没动 |
| **用新引擎自己的 `doctor` 在真实数据上自检** | 删 staging，指针没动，报是哪一项挂的 |
| 快照数据里的配置类文本 | 失败则不动手（快照本身失败说明盘有问题，不该继续） |
| staging 转正 + 指针原子切换 | `current` 要么旧值要么新值，不会有第三种 |
| 清理旧版（保留当前 + 上一版） | 只是少删几个目录 |

**自检拦什么**：数据根可写、依赖齐全、配置能解析、profile 能加载、模板能解码、
配方能被新引擎读懂、磁盘够。**不拦什么**：规则写错、标答缺字段 —— 那些是内容问题，
新引擎恰恰可能是来修它的，拦下来只会让人卡在旧版。

## "不能改"是内核保证的，不是靠自觉

```ini
ProtectSystem=strict
ReadOnlyPaths=/opt/autogame
ReadWritePaths=/var/lib/autogame
```

服务进程对引擎目录**没有写权限**。谁要是在设备上手改了 `releases/0.2.1/` 里的 `.py`，
`upgrade.py verify` 会把它列出来（逐文件 sha256 与发布清单比对），页面上也会显示
「被改过」。而且下次升级会覆盖掉 —— 要留就先提交到仓库再发包。

## 发版时要记住的四件事

1. **`profiles/<游戏>/` 不进包**（`tools/release.py` 只带 `_template` 和 `generic_*`）。
   把用户数据打进包，一次升级就覆盖掉标了几个月的模板。
2. **依赖变了**：`deploy/install.sh` 建的那个 venv 跨版本共用。
   新包加了库就先 `sudo /opt/autogame/venv/bin/pip install -r <release>/requirements.txt`，
   或者 `autogame-install --with-deps <pkg>`。`doctor` 会报「依赖齐全」不过。
3. **数据布局变了**：`DATA_SCHEMA` 加一，并在 `autogame/upgrade.py` 里补一条
   单向迁移。不加迁移就改布局 = 老设备升上来读不到自己的数据。
4. **`dirty` 的包只适合自己试**：`release.py` 会打印警告，别人复现不出来。

## 排障

| 现象 | 原因 | 处理 |
|---|---|---|
| 装完行为没变 | 进程还跑着旧代码 | `sudo systemctl restart autogame`；页面显示「重启后生效」 |
| `依赖齐全` 不过 | venv 里缺新库 | 见上面第 2 条 |
| `数据根在 releases 里面` | `AUTOGAME_DATA` 指错了 | 指到 `/var/lib/autogame` |
| 退不了：「数据已被升级过」 | 数据 schema 比目标引擎新 | `--force`（先快照），或 `upgrade restore <快照>` 连数据一起回 |
| 页面「不可用」 | 没绑定 profile | `echo tli_phone960 > /var/lib/autogame/profile`，或 `--profile` |
